# ISO/IEC 27001:2022 控制項對照

這份文件記錄這個 DEMO 的做法對應到哪些 Annex A 控制項，以及哪些項目刻意不做、為什麼不做。

**這不是合規證明。** ISO 27001 驗證的是組織的資訊安全管理制度，不是單一軟體。這裡沒有風險評鑑、適用性聲明（SoA）、內部稽核或管理審查，也不打算取得驗證。控制項編號請以標準原文為準。

**適用範圍假設**：只在一台開發機上執行、只用模擬金流、資料都是測試資料、不對外開放。只要有一項假設改變，「刻意不做」那張表就要重新評估。

## 已實作

| 控制項 | 做法 | 驗證方式 |
|---|---|---|
| 5.3 職責分離 | 初審、覆核角色分開；資料庫也限制不能同一人 | 功能測試 |
| 5.16、5.18 身分與存取權 | 帳號清單、上次登入時間、停用與恢復（需 TOTP 與理由） | 功能測試、瀏覽器流程 |
| 5.17 驗證資訊 | 每個管理員有各自的隨機初始密碼，不寫入檔案，首次登入必須更改 | 功能測試、瀏覽器流程 |
| 5.33、8.15 紀錄與保護 | 稽核紀錄只能新增，資料庫觸發器擋下更新、刪除與 `TRUNCATE`；重置測試資料時保留 | 功能測試、瀏覽器流程 |
| 8.2、8.3 權限與存取限制 | 依角色限制路由，後台有 IP 白名單（只看連線來源） | 功能測試、實測 |
| 8.2、5.15 資料庫最小權限 | 應用程式用 `topup_app` 連線：只有讀寫資料的權限，不是資料表擁有者、不是超級使用者；不能改結構與觸發器、不能修改或刪除稽核紀錄、不能修改 migration 紀錄、不能執行系統指令。資料表擁有者只給 migration 使用 | 功能測試（`DatabasePrivilegeTest`）、實測 |
| 8.5 安全驗證 | bcrypt、TOTP（只能用一次）、高風險操作再驗證、IP 限流、單一帳號連續失敗 5 次鎖定 15 分鐘；玩家與管理員改密碼後，其他裝置的 session 立即失效（玩家包含充值網站）；管理員重設 TOTP 時也一樣 | 功能測試 |
| 8.5 特權帳號的 session | 後台使用獨立的 session cookie（只送往 `/admin`、關閉瀏覽器即失效），與玩家端互不共用；閒置 15 分鐘、登入超過 8 小時都要重新登入（參考 PCI DSS 8.2.8） | 功能測試（`AdminSessionTest`）、實測 |
| 8.32 變更管理（方案） | 新增與修改方案要再驗證 TOTP；稽核紀錄保留修改前後的名稱、價格與上下架狀態 | 功能測試 |
| 8.8 弱點管理 | PHP 8.5.12 已修補 PHP2Shell，版本過低時建置失敗；`composer audit` | 手動執行 |
| 8.9 設定管理 | 映像鎖定 digest；設定集中在 compose 與 `.env.example` | 檢視設定 |
| 8.10 資訊刪除 | 退款結案時刪除申請上的帳號密文，只留銀行代碼與後四碼；玩家綁定的撥款帳戶保存到玩家自己刪除為止，刪除時整筆移除 | 功能測試 |
| 8.11、8.12 遮罩與防外洩 | 帳號在畫面上遮罩；日誌與稽核紀錄不寫完整帳號；例外堆疊不帶函式參數 | 功能測試 |
| 8.15 日誌 | 後台與充值端事件寫入 `audit_logs`（含來源 IP）；玩家端登入事件與簽章錯誤的金流通知（`webhook.rejected`，只記聲稱的編號）寫入 `security.log`。保留：應用程式日誌 30 天、安全日誌 90 天 | 功能測試 |
| 8.15、8.33 日誌不混入測試資料 | 功能測試不寫入實際的日誌檔 | 功能測試 |
| 8.20、8.22 網路 | 只開放 `127.0.0.1:8443`；資料庫不對外；內部 API 外部回 404 | 實測 |
| 8.24 加密（部分） | 對外 TLS 1.2 以上；帳號、TOTP 密鑰、session 以 AES-256 加密；API 使用 HMAC | 實測 |
| 8.26、8.28 應用程式安全 | CSRF、CSP、Cookie 安全旗標、簽章防重放、冪等、伺服器端驗證 | 功能測試 |
| 8.29 安全測試 | 功能測試、瀏覽器流程、併發測試（皆非獨立第三方） | 見 README |
| 8.33 測試資料 | 功能測試使用獨立資料庫，並檢查資料庫名稱 | 功能測試 |
| 8.3、8.15 小遊戲資料保護 | 局資料由觸發器鎖定、每局有 HMAC 檢查碼；不符時停止處理並寫入稽核紀錄。`minigame:check` 唯讀核對帳本、錢包、訂單與局 | 功能測試、併發測試 |
| 8.26、8.28 小遊戲請求 | 結果與獎勵只由伺服器計算；同一局只接受第一次的內容；加點必須對應帳本裡的下注，且不超過賠率表上限 | 功能測試 |
| 8.26、8.28 遊戲內充值 | 先建立訂單、再送出付款資料；付款資料由遊戲端以簽章 API 轉送給充值端驗證，不寫入資料庫、日誌或 session；一張訂單只接受一次付款（併發時也只有一個生效）；請求不能指定付款情境 | 功能測試、併發測試、瀏覽器流程 |

## 刻意不做（僅限這個 DEMO）

| 控制項 | 不做的內容 | 理由 | 如果要上線 |
|---|---|---|---|
| 8.13 備份 | 沒有備份 | 資料都是可重建的測試資料 | 必須有備份與還原演練 |
| 8.16 監控 | 沒有監控告警 | 單人本機使用；異常清單需要自己查看 | 必須有告警 |
| 8.24 內部加密 | 內部 API 走 HTTP、PostgreSQL 未啟用 SSL、磁碟未加密 | 流量只在單機 Docker 網路內，表單也警告勿填真實帳號 | 全部要加密 |
| 8.24 金鑰管理 | `APP_KEY` 與 API 密鑰放在 `.env`，沒有輪替 | 本機開發環境 | 改用密鑰管理服務並定期輪替 |
| 8.24 憑證 | 自簽憑證，沒有 HSTS | 只有 localhost 使用 | 正式憑證與 HSTS |
| 8.9、8.19 容器加固 | 容器沒有設定 `no-new-privileges`、`cap_drop`、唯讀檔案系統與資源上限；專案目錄（含 `.env`）由執行應用程式的使用者擁有 | 本機開發要能即時修改程式 | 程式碼唯讀、只開放 `storage` 可寫、`.env` 權限 600 或改用密鑰管理服務 |
| 8.24 支付資料範圍 | 遊戲內充值的付款資料會經過遊戲端，內部以未加密的 HTTP 轉送 | 只接受測試卡號 | 改用金流商託管的付款頁或 iframe，卡號不經過自己的伺服器 |
| 8.4、8.32 版本與變更管理 | 有 git 與 GitHub 儲存庫，但沒有分支保護與程式碼審查 | 單人 DEMO | 必須有分支保護、審查與變更紀錄 |
| 8.25 開發流程 | 沒有 CI 與定期掃描 | 單人 DEMO，測試手動執行 | 必須納入 CI |
| 8.31 環境分離 | 開發與展示共用同一環境 | 只有一個本機環境 | 必須分離 |
| 5.34 個資 | 沒有隱私政策，也沒有刪除玩家帳號的功能 | 只有測試資料 | 必須補齊，並確認法規 |
| 5.31 法規 | 未確認點數可儲值、互轉又可換現金的法規問題，也未確認以這種點數玩機率遊戲是否涉及賭博相關法規 | 不收真實款項、不對外營運 | **上線前必須請律師評估** |

## 仍存在的限制

- 稽核紀錄的保護在資料庫層。應用程式帳號改不了觸發器，但資料表擁有者帳號（`DB_OWNER_*`）可以，而它的密碼和應用程式帳號放在同一個 `.env`。要完全防竄改，需要把紀錄送到應用程式與主機管理者都改不到的地方。
- 轉盤局資料的觸發器有同樣的限制：資料表擁有者可以移除它。檢查碼能發現這種竄改，但拿到 `.env` 的人可以偽造檢查碼。
- 資料表擁有者也是 PostgreSQL 容器的管理帳號（超級使用者），只能用在 migration 與維運，不能讓應用程式使用。
- 後台 session 的切換依賴 PHP-FPM「每個請求一個程序」；改用 Octane 等長駐程序時要另外處理。
- 這次修正前，功能測試的紀錄已經寫進 `security.log`（標示為 `testing.`），保留作為紀錄，未刪除。
- 檢查碼的密鑰由 `APP_KEY` 導出。更換 `APP_KEY` 後，舊局的檢查碼會失效，伺服器種子也解不開。
- 加點 API 與其他玩家端 API 共用 `GAME_API_SECRET`。獨立密鑰在同一個 `.env` 下沒有實際隔離，上線時應改用密鑰管理服務並分開。
- 帳號鎖定可能被用來阻擋特定帳號登入 15 分鐘。這是為了防猜密碼的取捨。
- 一個人如果同時持有初審與覆核兩個帳號，系統無法分辨，職責分離要靠組織管理。

## 日常操作

**忘記密碼或遺失 TOTP**（新密碼只顯示一次，動作會寫入稽核紀錄）：

```sh
docker compose exec app php artisan topup:admin-reset <帳號> --password
docker compose exec app php artisan topup:admin-reset <帳號> --totp
```

**更新映像**：鎖定 digest 後不會自動取得安全更新，要定期手動更新。

```sh
docker pull <映像:標籤>
docker image inspect <映像:標籤> --format '{{index .RepoDigests 0}}'
```

把新的 digest 填入 `docker/php/Dockerfile` 或 `docker-compose.yml`，執行 `docker compose build app && docker compose up -d`，再跑一次測試。PHP 只能往上調整版本。

**弱點檢查**：

```sh
docker compose exec app composer audit
```
